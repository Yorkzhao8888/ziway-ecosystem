# SC-012 · 系统管理员运维治理（标准范例）

> **视角**：治理/系统｜**主角角色**：`AU` ｜ **涉及平台**：AOS/AMS + OAS
> **对应 A1.1**：02_B 角色派生 / 03_B OS 十二平台 / 03_C MS 十二管理集座 / 03_D OAS 底座
> **格式**：标准范例（业务流 + 精简时序图 + 增量 DDL + 事件契约 + 一致性验证）


## 一、业务背景

系统管理员(AU)通过 AOS 管理租户/权限/配置，AMS 核算计量，OAS 执行运维与监控。

## 二、前置准备

- **角色**：`AU`（由四根身份 HU/EU/GU/OU 派生，戴帽机制见 SC-014）
- **数据**：复用通用表 `iam.tenants` / `iam.users`（见 `00_场景范例索引.md` 通用表清单），以下仅列**本场景增量表**
- **权限**：`tenant_id` 多租户隔离；跨 OS 调用经 XBUS 事件总线

## 三、关键流程步骤

| # | 步骤 | 参与者流向 |
|:--|:--|:--|
| 1 | AU 登录 AOS(运维台) |
| 2 | 租户/角色/权限配置(AMS) |
| 3 | 服务配置与发布(OAS CI-CD) |
| 4 | 监控告警处置(Agent 智体) |
| 5 | 资源计量核算 AMS |
| 6 | 安全审计 GMS 联动 |
| 7 | 故障复盘归档 |
| 8 | 容量规划 |

## 五、关键 API（RESTful）

| 方法 | 路径 | 说明 |
|:--|:--|:--|
| POST | `/api/{os}/...` | 创建类操作（写，走 Saga） |
| GET  | `/api/{os}/...` | 查询（同步 gRPC/HTTP） |
| POST | `/api/{ms}/...` | 管控规则/审批 |
| EVENT| `xbus.<事件类型>` | 跨 OS 异步事件（幂等） |

> 完整路径与字段见 `00_API_清单.md`（OpenAPI YAML）。

## 六、增量数据表 DDL

以下表为**本场景新增**，通用表（`iam.tenants`/`iam.users` 等）不重复定义：

- `aos.tenants_config`
- `ams.metering`
- `oas.audit_logs`
- `datalake.ops_metrics`

## 七、事件契约

复用统一事件类型（幂等键 = 事件类型 + 业务 ID，72h 超时，死信队列见 SC-013）：

`ConfigChanged`, `DeploymentTriggered`, `AlertTriggered`, `MeteringReported`, `IncidentResolved`

## 八、与 A1.1 一致性验证

| 验证点 | 结果 |
|:--|:--|
| X 在 OS、M 在 MS | ✅ 交互在 APP/OS，审核管控在 MS |
| 层间正交（APP 不经 MS）| ✅ 均经 OS 中转 |
| 单一权威源 | ✅ 每类数据仅一个 owner |
| 四根身份 / 戴帽 | ✅ 主角由根身份派生 |
| 跨 OS 协作经 XBUS | ✅ 多场景涉及（详见 SC-013）|
| EOS=供给运营 / EMS=供给管理 | ✅ 命名规范统一 |

## 九、一句话总结

> **系统管理员运维治理** 场景完整走通了「治理/系统」下的角色→平台→管控→底座闭环，
验证了 A1.1 「AOS/AMS + OAS」协作的正确性与职责边界清晰性。
