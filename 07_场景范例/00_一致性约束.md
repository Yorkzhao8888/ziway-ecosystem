# 一致性约束（8 条铁律）

> 本文档是知味生态全量文档集的唯一规范源（Single Source of Truth）。
> 配套自动化守卫脚本 `scripts/check_consistency.py` 与 GitHub Actions
> `.github/workflows/consistency.yml` 会按本文 8 条铁律自动扫描全量文档，
> 发现 **error 级违规即 CI 失败**，永久杜绝回退。

---

## 使用约定

- **违规等级**：`error`（阻断合并）/ `warning`（提示，不阻断）
- **自动修复**：`python3 scripts/check_consistency.py --fix` 可机械修复 R1/R2/R3 部分违规
- **行级忽略**：某行确需保留旧名作对照时，行尾加 `<!-- guard:ignore 原因 -->` 跳过该行
- **迁移语境**：含"旧/原为/曾用/原名/迁移/→/历史/deprecated/legacy/LOCKED/A1."等词的行自动跳过

---

## R1 · 层命名：OS / MS / OAS

| 项 | 规范 | 禁用（反例） |
|:---|:---|:---|
| 平台层 | `X-OS`（如 COS / DOS / EOS / HOS / POS）| `BOS`、`X-BOS` |
| 管理层 | `X-MS`（如 CMS / DMS / EMS / HMS / PMS）| `MBS`、`X-MBS` |
| 技术底座 | `OAS`（上帝视角：全知/全能/全在）| `OSA` |

**助记**：`-OS` = Operating System（业务操作系统，平台层）；`-MS` = Management System（管理系统，管理层）。

> 四事业对应关系（不再使用 PM 旧称）：
> - TM（技术研发）→ POS / PMS（Lab）
> - DM（产品）→ DOS / DMS（Shop）
> - EM（供给运营）→ EOS / EMS（Market）
> - CM（客户关系）→ COS / CMS（Mall）

---

## R2 · 价值链命名：TM（禁用 PM）

价值链第一段命名为 **TM**（Technology Manufacturing，技术研发），禁用 **PM**（Product Management）。

| 阶段 | 缩写 | 核心产出 |
|:----:|:----:|:--------:|
| 1 | **T** | 技术（Technology）|
| 2 | **D** | 产品（Development）|
| 3 | **E** | 供给（Exchange）|
| 4 | **C** | 客户（Customer）|

**T=技术 / D=产品 / E=供给 / C=客户** — 无重叠，边界清晰。

> 例外：作为对照说明保留旧名时（如"而非 PM"），用 `<!-- guard:ignore -->` 标记。

---

## R3 · 核心原则：X 在 OS，M 在 MS

> **用户交互（X）统一在 APP 应用层与 OAS 底座层完成，不与管控逻辑耦合；
> 管理控制（M）统一在 MS 集座与 OS 平台层完成，不直接暴露给用户终端。**

禁用表述：`M 在 BS`、`X在OS/M在BS`、`BS 管控系统`。

---

## R4 · 网关路由：X-MS 风格（禁用旧 mbs 前缀）

Kong / API 网关路由统一使用 `X-MS` 风格小写路径：

| 直通 OS | MS | Kong 路由 |
|:--------:|:---:|:----------|
| AOS | AMS | `/api/ams/*` |
| POS | PMS | `/api/pms/*` |
| HOS | HMS | `/api/hms/*` |
| EOS | EMS | `/api/ems/*` |
| SOS | SMS | `/api/sms/*` |
| FOS | FMS | `/api/fms/*` |
| GOS | GMS | `/api/gms/*` |
| OOS | OMS | `/api/oms/*` |

禁用：`/pmbs`、`/embs`、`/ambs`、`/smbs` 等旧 MBS 风格前缀。

---

## R5 · 身份体系：四根身份 + 戴帽

**根身份（原子，不可再分）**：`OU`（生态方）/ `HU`（个人）/ `EU`（企业）/ `GU`（政府）。

**派生/戴帽角色**：`CU` / `DU` / `PU` / `SU` / `VU` / `FU` / `IU` / `AU`（在原根身份上"戴帽"获得）。

- `CU`（消费者）是**派生角色**，禁止作为根身份定义。
- 身份转换：`OU → VU/FU/AU/DU/IU`；`HU → CU/PU/IU`；`EU → CU/IU`；`GU → CU/IU`。

---

## R6 · 单一事实源：通用表不重复定义

- 每个主题只有一个权威文档，不存在"基线 + 修正"的双重结构。
- 通用表（`iam.tenants`、`iam.users`、`iam.permissions`、`xbus.events`、`datalake.*` 等）
  **集中定义于 `07_场景范例/00_数据字典.xlsx`**，各场景文档**只列增量表**。
- 违反自检句式：**"声明不重复定义通用表，却又把 iam.tenants/iam.users 列为增量表"** → 逻辑矛盾，须修正。

---

## R7 · 事件驱动：幂等与死信

跨 OS/MS 通信统一事件契约：

- **幂等键** = `eventType + eventId`
- **超时**：72h 未确认进入重试/告警
- **死信队列**：多次重试失败转入 DLQ 人工处理
- **权威源**：事件 schema 以 `07_场景范例/00_OpenAPI.yaml` 的 `XBusEvent` 为准

---

## R8 · 场景覆盖：五层视角

每个 `SC-xxx` 场景文档应命中至少一个五层视角关键词（产研/业务/职能/治理/横切），
确保场景有明确业务归属。完整覆盖矩阵见 `07_场景范例/00_场景范例索引.md`。

## 附：CI 验证

```bash
# 本地运行完整守卫（含场景覆盖检查）
python3 scripts/check_consistency.py --coverage

# 机器可读输出（CI 消费）
python3 scripts/check_consistency.py --coverage --json

# 自动修复可机械处理的违规（R1/R2/R3）
python3 scripts/check_consistency.py --fix
```

推送至 `main` / PR 至 `main` 时，GitHub Actions 自动运行 `.github/workflows/consistency.yml`，
任何 `error` 级违规将阻断合并。
